## 2. 项目定位与目标用户

### 2.1 产品定位

课迹是一款个人使用的 Android 应用，用于把课堂录音、课件画面、OCR 内容、语音转写和大模型文本生成组合成一个可复习的知识结构。

核心链路：

```text
上行采集：
手机麦克风 → 录音分段 → 上传 Linux 服务端
MediaProjection → 定时截屏 → 上传 Linux 服务端

准实时：
服务端 SenseVoice → 字幕 → WebSocket 推送
服务端 OCR → 页码/标题/关键文本 → 时间轴事件推送

课后：
全量音频 → 服务端重转写 → LLM 定稿
OCR 时间轴 + 转写 → 全文总结、分节小结、思维导图 → App 编辑/导出
```

手机端不运行任何 ASR/OCR/大模型服务，只负责采集和上传音频、图像，并接收和展示服务端返回的结果。

### 2.2 目标用户

目标用户为开发者本人或少数同学，场景是个人课程复习：

1. 上课时用手机录音并截屏课件画面。
2. 课后在 App 中查看带时间戳、页码、标题的转写和总结。
3. 对总结、分节小结、思维导图进行编辑，用于复习和导出。

### 2.3 用户痛点

- 上课来不及记录，课后回听录音效率低。
- 录音和课件页码无法自动对应，复习时反复拖动进度条。
- 通用 AI 总结过于概括，缺少按节、按页的整理。
- 公有云 ASR/OCR 存在隐私和持续费用顾虑。

### 2.4 产品边界

第一版是“个人记录与整理工具”，不是多人协作、教育管理或内容发布系统。它允许：

- 采集真实课堂环境声和屏幕画面。
- 把音频、图片、文本证据统一整理到一门课程。
- 通过大模型生成结构化复习材料。

第一版不做：

- 多账号、权限管理、多人实时协作。
- 与商业教学工具（雨课堂等）绑定。
- 加密的端到端传输与密钥体系。
- 系统内录（仅作为后续增强）。
- 公式结构 OCR、图表还原。
- 说话人分离（数据结构预留 `speaker`）。
- 原生思维导图文件导入（如 XMind）。

### 2.5 系统部署与信息交换边界

课迹落地运行后只存在两个运行节点：Android 手机和 Linux 服务端，Windows 开发机不作为运行节点。

| 节点 | 职责 | 允许 | 不允许 |
| --- | --- | --- | --- |
| Android 手机 | 课堂采集、结果使用 | 录音、截屏、上传音频与图像、接收 WebSocket 结果、展示与编辑总结/思维导图、导出 | 运行 ASR/OCR/大模型、加载模型文件、作为服务端 |
| Linux 主机 | 唯一服务提供者 | 提供 FastAPI 接口、SenseVoice 转写、PaddleOCR/OpenVINO 识别、LLM 优化与生成、SQLite 与文件存储 | 依赖手机或开发机提供服务 |
| Windows 开发机 | 编写与构建 APK | 编辑 Android 源码、执行 `gradlew assembleDebug`、构建与提交 APK | 启动服务端、安装模型、保存推理缓存、为手机提供任何服务 |

手机与 Linux 服务端的交互全部走网络接口：音频上传转写、截屏上传 OCR、WebSocket 字幕与时间轴、生成结果读取等。语音转写、图像识别和 LLM 生成对手机端而言都只是接口能力，模型文件、运行环境和任务调度只属于 Linux 服务端内部。

## 3. 使用场景与用户故事

| 场景 | 示例用户故事 |
| --- | --- |
| S1 课堂采集 | 作为学生，我希望在课堂开始后同时录音和截屏，避免课后再听录音，也不错过页码和标题。 |
| S2 准实时字幕 | 作为学生，我希望在课堂中看到服务端实时返回的字幕，并知道其时间范围，而不是等待课后才得到全文。 |
| S3 页码关联 | 作为学生，我希望字幕和 OCR 页码/标题对应，允许复习时直接跳到对应页。 |
| S4 课后整理 | 上完课后，我希望 App 自动完成重转写、定稿、总结、小节和思维导图，并保留可编辑入口。 |
| S5 导入音频 | 已有课堂录音时，我希望直接导入整个音频，由服务端自动转写和生成，不必再用手机录一遍。 |
| S6 导出 | 希望把课后整理结果导出为 Markdown/OPML，方便在笔记工具或思维导图工具中继续编辑。 |
| S7 离线兜底 | 如果局域网服务器不可达，仍允许继续录音、截屏、缓存和事后上传，避免课堂数据丢失。 |
| S8 无服务器兜底 | 在没有服务器时手机只缓存音频和截图，不生成草稿字幕；服务器恢复后自动补传并完成转写。 |

## 4. 范围划分

### 4.1 第一版范围（P0）

第一版必须具有：

1. Android 麦克风录音，录音分段、瞬时处理与本地排队上传。
2. MediaProjection 屏幕采集、定时截屏、画面变化过滤、上传服务端。
3. 服务端 OCR，识别页码、标题、正文关键文本，并形成时间轴。
4. 音频与课件时间轴对齐，自动切分“节”。
5. 准实时字幕：服务端对上传音频段实时转写并推送。
6. 课程结束后服务端高精度重转写并尽快定稿。
7. 大模型生成全文详细总结、分节小结、思维导图。
8. App 内查看与编辑总结、分节小结、思维导图节点。
9. 基础课程列表、按关键词搜索、按时间戳或页码定位。
10. 导出 Markdown 和 OPML。
11. 长课堂（5 小时）数据保存与断点续传。

### 4.2 建议实现（P1）

- 大模型生成的“定稿”与原始转写之间的差异标记。
- 思维导图拖拽、添加、修改、删除、父子层级调整。
- OCR 识别页面标题失败时的用户手动补充。
- 编辑分节边界、合并/拆分节。
- 导出前重新整理本地导出，并支持分段另行导出。

### 4.3 后置（P2）

- 说话人分离、说话人标注、说话人合并/拆分。
- 公式 OCR。
- 系统内录。
- 多个讲师、多门课程自动管理、复杂权限。
- XMind 原生文件、PDF/PNG 导入导出。
- 手机端 OCR（后续增强，不在第一版范围）。

### 4.4 产品边界：手机端定位

第一版的产品边界明确为“薄客户端 + 单一服务端”：

1. 手机端只负责：麦克风录音、MediaProjection 截屏、音频/图片上传、接收 WebSocket 字幕/时间轴/状态、查看与编辑生成结果。
2. 手机端不运行：SenseVoice、whisper.cpp、sherpa-onnx、PaddleOCR、ML Kit 或其他任何 ASR/OCR/大模型服务。
3. 手机端不生成“待复核草稿字幕”，不保存本地转写结果；离线时只保存未上传的原始音频与图片。
4. 所有识别能力（语音转写、OCR、说话人分离预留、LLM 生成）统一放在 Linux 服务端。
5. Linux 服务端能力接口化：语音转写、图像识别、LLM 优化与生成只通过 HTTP/WebSocket 接口暴露，不提供手机端模型下载、本机进程或文件级依赖。
6. Windows 开发机只编写 Android 工程并构建 APK，不启动服务端、不保存模型与推理缓存，不作为落地运行节点。

## 5. 功能需求

需求编号采用 `ID`，便于在后续设计、测试、验收中引用；`P0` 为第一版必做。

### 5.1 用户认证与设备连接（AUTH）

| ID | 需求 | 优先级 | 说明 |
| --- | --- | --- | --- |
| AUTH-01 | 首次使用时配置服务地址、用户名、密码 | P0 | App 不提供注册；账号由服务端管理维护。 |
| AUTH-02 | 服务端使用用户名+密码进行 Basic 认证 | P0 | 项目书写明第一版为单激活令牌，现状实现为用户名/密码，需验收确认是否保留令牌兼容。 |
| AUTH-03 | 支持修改密码 | P0 | 修改后 App 本地与服务器同步使用新密码。 |
| AUTH-04 | 服务端配置保持在服务端 `.env` | P1 | 手机端不保存大模型 API Key；手机端可为整门课下发大模型配置。 |
| AUTH-05 | 隐私保护：本地不写入访问日志、不上传非课堂信息 | P0 | 服务器日志不记录音视频内容，不记录第三方 API 调用结果。 |

> 注：AUTH-02 是当前项目书与实现之间的最大偏差，详见 11 节。

## 8. 约束与假设

### 8.1 运行约束

- 手机端以 Android 14 行为标准，最低 Android 8.0。
- 服务端以单用户局域网单机运行为主，不要求多机房、分布式、高可用。
- Windows 开发机只编写 Android 源码、构建 APK 和提交代码，不运行服务端、不安装模型、不保存推理缓存。
- 落地运行只由 Android 手机与 Linux 主机发生信息交换；Windows 开发机不在运行链路中。
- Linux 服务端能力全部接口化：语音转写与图像识别通过 HTTP/WebSocket 提供给手机端，不要求任何桌面端或本机前端配合。
- 第一版不绑定雨课堂或特定课件格式。
- 第一版数据全部以服务端 SQLite + 文件目录保存，不支持云同步。
- 第一版将音频与截图保存在局域网服务器，只有调大模型 API 时才会离开局域网。

### 8.2 设计假设

- 单次课堂最多约 5 小时。
- 一次课堂会存在多段录音、多帧截图，`offset_ms` 是唯一时间基准。
- OCR 工具栏可能没有页码；因此标题、正文变化和语音主题变化需要作为补充切分条件。
- 大模型可能返回不完整或非 JSON；服务端必须自带校验与重试。
- 手机端可以暂时没有服务器；因此采集、本地缓存、上传队列、WebSocket 接收必须互相解耦，离线期间不产生任何本地转写。

## 9. 流程需求

### 9.1 课堂实时流程

1. 用户填写课程名，授权录音与媒体投影。
2. 手机启动前台服务，开始采集并上传音频段、截帧。
3. 服务端保存数据，实时回推字幕，并在 OCR 完成后回推 `timeline`。
4. 手机端只显示服务端实时推送的确认字幕与页码/标题时间轴，不合成本地草稿字幕。

### 9.2 课后流程

1. 用户点击“结束课堂”或“导入完成”。
2. 手机端上传未完成的数据。
3. 服务端按顺序执行课后转写：`queued -> transcribing -> transcribed`。
4. 首次完成后用户可查看/触发生成。
5. 服务端执行 LLM 生成：`generating → completed/failed`。
6. 手机端展示总结、分节、思维导图，允许编辑后导出。

### 9.3 断点续传流程

1. 网络中断或服务器不可达时，录音/截帧先写入本地会话目录。
2. 恢复后 App 重试上传，按文件名内的 `offset_ms` 与服务器状态幂等合并。
3. 超过本地配额时优先清理已成功上传的最早文件。

## 10. 验收标准

第一版验收至少包含以下场景，并附测试数据：

1. 在目标 Android 手机上安装 APK，可开始/结束课堂、显示状态栏、通知。
2. 课堂中能够看到服务端实时转写字幕；服务端可达时同时收到页码/标题时间轴。
3. 课堂结束时提交课后转写，任务状态最终进入 `transcribed`。
4. 导入 5 小时外的长录音也能完成转写与合并（允许耗时很长，但要可中断/可恢复）。
5. 生成结果包含：全文总结（时间戳、页码）、分节小结、思维导图 JSON。
6. App 可编辑总结/分节/思维导图并保存，刷新详情后保持一致。
7. 可导出 Markdown、OPML，导出文件内容与 App 内容一致。
8. 服务不可达时关闭采集，本地文件完整，恢复后重新上传，不丢失。
9. App 端不显示/不存储大模型 API Key；接口响应不包含敏感字段。
10. 大模型 429 时按自动重试规则执行，不重复产生部分结果。
11. APK 只由 Windows 开发机构建，且本机不启动任何识别/生成服务；手机配置服务地址后仅与 Linux 主机成功通信。
12. 语音转写与图像识别在手机上表现为接口调用：上传音频/截图后能收到字幕/时间轴结果，手机端不包含本地模型或推理组件。

# 第二部分：可行性分析

## 14. 可行性分析

### 14.1 可行性综述

“课迹”第一版采用“轻量 Android 采集客户端 + 局域网 FastAPI 集中识别服务”的架构：手机端只采集和上传音频、图像，SenseVoice、PaddleOCR 与 LLM 全部部署在服务端。技术路线成熟、实现成本可控，且模型只维护一份，便于替换和更新。

此架构中，Windows 开发机只用于编写 Android 工程、构建 APK 和提交代码；系统落地运行后只有 Android 手机与 Linux 主机发生信息交换。

项目当前已具备可运行的 Android APK 和服务端代码，主要风险不再是“能不能做”，而是“长课堂稳定性、OCR 准确率、服务端 CPU 调度和大模型生成质量”四类实测优化问题。

从软件工程角度看，第一阶段以“最小可演示版本”作为里程碑，使用现有代码库继续完成工程化，是最稳妥的推进方式。

### 14.2 技术可行性

| 维度 | 结论 | 依据 |
| --- | --- | --- |
| Android 采集 | 高可行 | Kotlin + AudioRecord + MediaProjection 已实现，APK 已构建 |
| 服务端 SenseVoice 转写 | 高可行 | 服务端已可用；模型与推理依赖集中在服务器，绕开手机端 AAR 与 ABI 差异 |
| 服务端 FastAPI | 高可行 | 现有 `routes.py` 已提供课程、音频、截图、生成、WebSocket 接口 |
| SQLite 持久化 | 高可行 | 数据库已支持课程、音频、截图、时间轴、任务 |
| PaddleOCR | 中等可行 | 依赖服务器环境；需 1-2 天验证识别准确率 |
| 大模型生成 | 中等可行 | 需按 8.2 做输出 JSON 校验与重试 |
| 长时录音 | 中等可行 | 分段上传与本地配额已考虑，但尚无 5 小时真机验证 |
| 5 小时恢复 | 中等可行 | 本地缓存与排队上传已实现，恢复规则需增加集成测试 |

结论：技术可行性通过，建议保留“SenseVoice + PaddleOCR + FastAPI”作为默认基线，不重新选型。

| 数据备份 | 中等 | SQLite + 文件目录可整体备份，但需避免长转写时数据库锁阻塞；当前写入频率可控 |
| 模型更新 | 高 | 模型只放在服务端，替换模型或切换 whisper.cpp 备选无需重新打包 APK |
| 日志与排查 | 中等 | 已有日志；建议增加任务失败现场快照（OCR 图片、音频片段、异常栈） |
| 安全 | 中等 | 用户名+密码 Basic 认证 + HTTPS；需补充“发送大模型前明确提示” |

### 14.6 法律与合规可行性

- 仅个人/内部使用，不涉及商业对外分发。
- 涉及他人课堂内容时，应在采集前征得课堂相关人员同意。
- 大模型 API 供应商服务条款由使用方确认；建议提供“仅发送转写文本/不发送”开关，并在首次生成时提示。
- 若服务器暴露公网，必须使用 HTTPS 和访问令牌，并考虑设备绑定或 IP 白名单。

### 14.7 风险与可行性结论

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| OCR 页码识别率不稳定 | 中 | 结合标题、正文变化、语音主题变化；增加手动修正 |
| 5 小时过程产生数据量过大 | 中 | 分段上传、自动清理已成功数据、配额控制 |
| 服务器内存/CPU 不足 | 中 | 单用户；转写并发限制 2 任务、OCR 2 线程；可切换 small int8 |
| LLM 输出结构不稳定 | 中 | 服务端校验 + 重试 + 降级 |
| 手机端仅采集也会崩溃 | 低 | 移除本机模型与原生库后，主要崩溃面转为录音/截屏前台服务，按真机回归验证 |
| 局域网断连 | 中 | 本地缓存 + 上传重试 + 断点续传 |

结论：技术、经济、运行、法律均可接受；第一版不需要引入新的主要技术栈。进入系统设计/实现之前，应先完成“真机长课堂与 OCR 准确率”两个验证点。

### 15.3 任务分解（WBS）

#### WBS 1：工程与测试环境

1. 在 Windows 上配置 Android SDK 与 JDK 构建环境；在 Linux 上配置 FastAPI 及识别依赖。
2. 确认 Windows 只用于 `gradlew assembleDebug`，不启动 FastAPI、不保留模型与推理缓存。
3. 创建测试账号。
4. 准备 ARM64 真机与模拟器。
5. 将真实课堂语音回归集放到 Linux 服务器数据目录。
6. 用 `smoke_api.py`、`smoke_realtime_subtitle.py`、`smoke_sense_merged.py` 建立基础冒烟。
7. 边界核查：手机只访问 Linux 接口，全部数据经「手机 ↔ Linux」，Windows 不参与运行链路。

#### WBS 2：Android 采集

1. 使用 `CaptureService` 前台服务开始/停止采集。
2. 录制 AAC/OPUS 分段，上传失败重试。
3. MediaProjection 截屏与 JPEG 压缩。
4. 导入音频转写。
5. 断点保存与本地配额。
6. 移除本机/局域网转写入口：删除或停用 `AppPreferences.transcriptionMode` 中的 `phone`/`network` 文案与切换控件，并清理相关依赖与模型资产（不影响上传与队列）。

#### WBS 3：服务端链路

1. Linux 上部署 FastAPI + WebSocket + SQLite，对外只暴露接口。
2. SenseVoice ONNX 转写 worker。
3. PaddleOCR worker，限制 2 线程。
4. 任务状态机与恢复。
5. LLM JSON 校验与失败处理。
6. 将转写、OCR、生成能力封装为稳定接口，保证手机端不接触模型与推理进程。

#### WBS 4：产品功能与编辑导出

1. 课程列表/搜索/时间戳与页码定位。
2. 详细总结、分节小结、思维导图编辑。
3. Markdown/OPML 导出。
4. 本地待上传数据随会话生命周期管理。
5. 退出采集时保留用户选择的数据。

### 15.6 里程碑验收

#### M0：环境基线

- Windows 开发机：Android Studio / JDK / SDK，`gradlew assembleDebug` 成功，且本机不启动服务端。
- Linux 主机：FastAPI / PaddleOCR / SenseVoice 模型部署完成，服务端可启动，冒烟脚本可在服务器侧运行。

#### M1：真机采集

- 真机完成一次 5 分钟课堂录音与截屏。
- WebSocket 收到 `subtitle`、`timeline`、`status` 三类消息。
- 无手机端残留识别模块崩溃点、无上传卡死。

#### M2：准实时字幕

- 服务端收到音频后 15 秒内返回确认字幕（网络环境允许时）。
- 同一时间窗重复上传时，以服务端最新确认字幕为准，手机端不做文本合并。
- OCR 页码/标题与字幕时间关系正确。

#### M3：生成链路

- 生成结果可保存并显示在详情页。
- 总结/分节/思维导图可编辑并保存。
- Markdown/OPML 导出可打开，无乱码。

#### M4：长课堂/数据

- 5 小时录音全部上传完成；中断后恢复。
- 本地配额不超过设置上限，且不删除当前音频。
- 转写完成前原始音频不删除。
